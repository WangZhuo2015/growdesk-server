# Snapshot bootstrap cursor and retention follow-up

**Status: IMPLEMENTED_NOT_REVIEWED**
**Worktree:** `/private/tmp/growdesk-server-sync-bootstrap-20261003`
**Base:** `35f8c1ebe0f4a8ef575b59aa609c1b9e777dde31`
**Scope:** Register the existing Go family snapshot-page operation, expose an exact-byte page digest and a signed ready-snapshot tail cursor, and reject family-feed cursors older than the current 90-day retained history.

## Implementation

- Added the snapshot page route to the fixed TypeBox contract and bound its existing `getNativeSnapshotPage` handler in [native_snapshots.go](/private/tmp/growdesk-server-sync-bootstrap-20261003/internal/backend/native_snapshots.go:14). The page response keeps typed `content` and adds `contentJSON` (the UTF-8 string of server `jsonBytes(page)`) plus lowercase SHA-256 `sha256`. Clients can hash `contentJSON.utf8` and decode those same bytes without reproducing Go's JSON encoder behavior.
- Ready snapshot metadata now includes a signed `nextCursor` generated by the existing sync HMAC key. It is scoped to the requesting family, records the snapshot epoch, sets both `position` and `highWater` to the ready snapshot's stored high-water, and uses `mode: tail`. The handler checks membership, snapshot creator, expiry, current epoch, and current permission version before returning it. Queued snapshots do not advertise a cursor. See [native_snapshots.go](/private/tmp/growdesk-server-sync-bootstrap-20261003/internal/backend/native_snapshots.go:78).
- The TypeScript API metadata path now captures creator and permission version at snapshot creation and signs the same ready tail cursor only after checking expiry and current sync state. This keeps normal backend builds aligned with the stricter shared contract in [sync-service.ts](/private/tmp/growdesk-server-sync-bootstrap-20261003/apps/api/src/services/sync-service.ts:757). The TypeScript worker still only toggles snapshot status and does not generate native snapshot pages; it was not used as evidence for page behavior.
- Family-feed retention currently computes the floor from the maximum cursor among extant `family_changes` rows older than 90 days. A cursor below that floor gets `410 SYNC_RESET_REQUIRED`; a fresh tail remains readable. No change rows are deleted by this work. If a future retention cleaner deletes old rows, it must preserve a durable floor before deletion; otherwise the floor will disappear and old cursors may become usable again. No schema or cleaner was added because the current scope has no retention-deletion contract.
- Snapshot pages remain stored in `sync_snapshots.manifest` PostgreSQL JSONB and are served by the existing Go handler; this flow does not use S3. The isolated runner excludes inherited AWS/S3/provider settings.
